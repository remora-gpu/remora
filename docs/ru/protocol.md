# Сетевой протокол (черновик v0.1)

::: warning Черновик
До 1.0 протокол нестабилен: каждая минорная версия ломает совместимость. С 1.0 стороны совместимы в пределах мажорной версии.
:::

Все целые числа передаются в little-endian. Эталонная реализация — крейт `remora-proto`. Нормативна [английская версия](../protocol).

## Жизненный цикл соединения
1. Подключение транспорта. По умолчанию TCP/QUIC с TLS 1.3; shared memory и RDMA настраиваются через управляющее TCP-соединение.
2. **Handshake** (фреймы `Control`): `ClientHello` → `ServerHello` → аутентификация → `SessionReady`.
3. Трафик API: фреймы `Request` / `Response` / `Event`.
4. `Goodbye` или закрытие транспорта. После неожиданного обрыва сессию можно возобновить в пределах тайм-аута, заданного на сервере.

## Заголовок фрейма
Каждый фрейм начинается с фиксированного 24-байтового заголовка. За ним идут `inline_len` байт структурированных данных и `bulk_len` байт bulk-данных.

| Смещение | Размер | Поле | Описание |
|---:|---:|---|---|
| 0 | 4 | `inline_len` | Размер структурированных данных, не более 16 МиБ |
| 4 | 1 | `kind` | 1 Request, 2 Response, 3 Event, 4 Control |
| 5 | 1 | `flags` | См. ниже; неизвестные биты — ошибка протокола |
| 6 | 2 | `channel` | Логический канал упорядочивания (например, CUDA stream) |
| 8 | 4 | `method` | `(api_family << 16) \| index`, назначается генератором |
| 12 | 4 | `bulk_len` | Размер bulk-секции фрейма |
| 16 | 8 | `request_id` | Монотонный в пределах соединения; ответ повторяет его |

### Флаги
| Бит | Имя | Значение |
|---:|---|---|
| 0 | `ASYNC` | Клиент не ждёт ответа; ошибки откладываются до следующего синхронизирующего вызова |
| 1 | `COMPRESSED` | Bulk-секция сжата согласованным алгоритмом |
| 2 | `BATCH_CONTINUES` | Дальше идут ещё фреймы этого батча; сервер может отложить исполнение |
| 3 | `BULK_CONTINUATION` | Фрейм продолжает разбитую на чанки bulk-передачу |

### Семейства API
0 — управление Remora, 1 — CUDA Driver API, 2 — NVML, 3 — cuBLAS/cuBLASLt, 4 — cuDNN, 5 — cuFFT, 6 — cuSPARSE, 7 — cuSOLVER, 8 — cuRAND, 9 — NVRTC/nvJitLink, 10 — NCCL, 11 — cuTENSOR, 12 — NPP.

## Handshake
`ClientHello`: magic `RMRA`, версия протокола (`major: u16`, `minor: u16`), битовая маска возможностей (`u64`), ОС/архитектура клиента, запрошенная приложением версия CUDA API, поддерживаемые алгоритмы сжатия, nonce клиента.
`ServerHello`: magic, версия, маска возможностей, id сервера, список доступных GPU (непрозрачные id), выбранное сжатие, nonce сервера.

Согласование: требуется одинаковый `major` (до 1.0 — ещё и одинаковый `minor`). Итоговый набор возможностей — пересечение масок.

## Кодирование данных
Inline-часть вызова — сгенерированная кодировка аргументов функции в фиксированном порядке:
- скаляры — значения в little-endian;
- хэндлы — 64-битные id в рамках сессии (никогда не сырые указатели сервера);
- указатели на память устройства — 64-битные виртуальные адреса, которые проверяет воркер;
- входные буферы хоста переносятся в bulk-секцию.

Выходные аргументы возвращаются в ответе так же.

## Bulk-передачи
Большие копирования host↔device делятся на чанки (по умолчанию 4 МиБ). Чанки идут подряд, во фреймах с флагом `BULK_CONTINUATION`. Так несколько передач и вызовов мультиплексируются, а получатель может совмещать сетевую передачу и копирование по PCIe.

## Ошибки
`Response` содержит код результата CUDA. Для `ASYNC`-вызовов сервер запоминает первую ошибку в каждом канале. Он возвращает её со следующим синхронизирующим вызовом этого канала — так же, как работают отложенные (sticky) ошибки в CUDA.
